# Togara World

A mobile-first hospitality network prototype with guest, business and founder experiences. The project includes a working local demo UI, three original high-tech cyborg infographics, and an initial Convex backend/authentication foundation.

## What works in this ZIP

- Responsive Togara World entry/authentication experience (local demo session only).
- Guest discovery, restaurant selection, menu browsing, cart, pickup/dine-in choice, demo checkout and order history.
- Business workspace preview with incoming orders and status controls.
- Founder network preview with explicit authorization warning and no fabricated network metrics.
- Single-establishment cart, order snapshots in the proposed backend schema, and clear development-only payment labeling.
- Local demo state persists in browser storage.
- Reduced-motion preference support.
- Three original cyborg/hospitality infographic assets in `public/infographics/`.
- A provider-neutral payment contract and development-only mock adapter in `lib/payments/`.
- Three proposed presentation presets in `lib/templates.ts`, clearly marked as proposals.

## Important implementation boundary

The visible app is currently a **local interactive prototype**. Its demo login, role switcher, sample restaurants, sample menu and mock checkout are not production authentication, real member records, real restaurant inventory, real payment processing or a live multi-user order network. The owner/founder views are visual workflow previews. The frontend has not yet been connected to Convex subscriptions or Convex Auth. The included Convex code is the backend foundation and must be deployed/configured and wired to the frontend before production use.

No real payment is taken. The local demo marks orders as `development_mock`; it must never be interpreted as genuine payment confirmation.

## Requirements

- Node.js 20.9 or later
- npm
- A Convex account/deployment for backend activation

## Run the interactive prototype

```bash
npm install
npm run dev
```

Open http://localhost:3000.

The sign-in form is deliberately a local demo entry. You can use the **Enter demo experience** button.

## Activate the Convex backend foundation

1. Create a Convex project and link this directory:

   ```bash
   npx convex dev
   ```

2. Configure the Convex deployment URL and auth environment according to the current Convex Auth + Next.js setup guide: https://labs.convex.dev/auth
3. Copy `.env.example` to `.env.local` and add `NEXT_PUBLIC_CONVEX_URL` and the deployment settings generated by Convex.
4. Run `npx convex dev` to generate the typed files in `convex/_generated/` and apply the schema.
5. Wire the frontend to `ConvexProviderWithAuth` and Convex Auth's React hooks before replacing the demo sign-in and local order state.

The included auth implementation uses Convex Auth with the Password provider. No Clerk dependency is present.

## Backend foundation included

- `convex/auth.ts`, `convex/http.ts`, `convex/auth.config.ts`: Convex Auth setup.
- `convex/schema.ts`: identity, profile, membership, business, establishment, menu, order, payment, inventory, staff, membership and audit tables.
- `convex/access.ts`: backend identity, establishment-access and founder authorization helpers.
- `convex/orders.ts`: authenticated order creation with server-side price/availability checks, idempotency, guest order query, establishment-scoped owner query and validated order transitions.

The inventory model is explicitly **product-count inventory** at this stage. It does not implement ingredient-level depletion or recipe/BOM accounting.

## Architecture decisions intentionally left open

- Three enterprise templates: not defined; schema supports reusable presentation configuration. Current infographic imagery is illustrative, not a final template definition.
- `SAL`: not defined; no invented SAL layer has been introduced.
- Canvas: no HTML Canvas dependency is introduced yet. The visual system uses CSS and image layers so ordering controls remain accessible and performant.
- Payments: provider interface remains unselected. Do not replace the development mock with Stripe or another provider without confirming the requirement. The backend order starts in `awaiting_payment` and `pending`; only a trusted provider webhook/action should mark a real payment paid.
- Membership tier scope: schema supports network-wide and establishment-specific tiers.
- Fulfilment: prototype shows pickup and dine-in only. Delivery and dispatch workflows are not represented as confirmed features.
- In-house table identifier: proposed, not yet persisted in the backend schema.

4. Connect cart/checkout to `orders.create`, then integrate a selected payment provider through verified server-side callbacks.

7. Add image upload, inventory movement, staff scheduling and offer eligibility mutations.

## Deployment

Deploy the Next.js frontend to a new Vercel project named `togara-world` and the backend to its own Convex deployment. Configure separate preview and production environment variables. This source archive has **not** been deployed to Vercel and no live URL is claimed.
